ESTADO ACTUAL DEL PROYECTO DAT-01

Fecha de actualización: 2026-08-23

DAT-01 implementa una primera etapa modular de lectura, validación, trazabilidad y resumen de archivos de movimientos registrales publicados por el TSE.

OBJETIVO Y ALCANCE
==================

La implementación cubre únicamente RAW / INGESTA / VALIDACIÓN.

El sistema puede:

- abrir archivos ZIP directamente sin descompresión manual;
- localizar automáticamente el TXT interno;
- ignorar archivos auxiliares del ZIP, como DOCX;
- aceptar un TXT directo para desarrollo y pruebas;
- calcular SHA-256 del ZIP y del TXT;
- leer registros de ancho fijo preservando espacios;
- validar registros vacíos, cortos y largos;
- validar campos obligatorios, tipos numéricos, fechas y enumeraciones configuradas;
- contar filas totales, válidas e inválidas;
- registrar errores técnicos sin exponer datos personales;
- guardar un resumen de la importación en SQLite;
- consultar el historial de importaciones;
- generar salida normal o JSON;
- ejecutar el modo estricto de configuración de movimientos;
- ejecutar `verify-dat01` para validar las tres muestras conocidas;
- ejecutar pruebas automatizadas con pytest.

Todavía no reconstruye la capa canónica ni almacena registros individuales.

BASE DE DATOS SQLITE
====================

La base local es data/db/imports.sqlite.

Tablas:

- import_runs: resumen técnico de cada ejecución.
- import_issues: incidencias técnicas limitadas a 100 por ejecución.

Se almacenan:

- dataset;
- nombre del ZIP fuente;
- nombre del TXT interno;
- SHA-256 del ZIP;
- SHA-256 del TXT;
- fecha y hora UTC;
- versión del esquema;
- longitud esperada;
- filas totales, válidas e inválidas;
- conteos de movimientos cuando existe configuración;
- errores de longitud, estructura y campos;
- estado;
- observaciones técnicas.

No se almacenan:

- nombres;
- apellidos;
- cédulas;
- identificaciones;
- nombres de padres, madres o cónyuges;
- líneas completas;
- valores RAW;
- registros individuales.

SQLite funciona como bitácora de importaciones, no como base de datos de personas.

CLASIFICACIÓN DE MOVIMIENTOS
============================

El motor soporta:

- INCLUSION;
- CHANGE;
- EXCLUSION;
- UNKNOWN;
- NOT_CONFIGURED.

Se buscó documentación en todo el repositorio y no se encontró un diccionario oficial que defina:

- posición exacta del campo de movimiento;
- longitud del campo;
- código oficial de inclusión;
- código oficial de cambio;
- código oficial de exclusión.

Por lo tanto, no se infieren códigos a partir de nombres, cédulas, patrones o registros reales.

Actualmente los tres esquemas tienen el movimiento no configurado y la consola muestra:

- Inclusiones: NO CONFIGURADO
- Cambios: NO CONFIGURADO
- Exclusiones: NO CONFIGURADO

Los valores SQLite correspondientes son NULL, no cero.

El sistema acepta la siguiente configuración cuando exista documentación oficial verificable:

movement.field:
- name
- start
- end
- type opcional
- required opcional

movement.codes:
- inclusion_codes
- change_codes
- exclusion_codes

El parámetro --require-movement-config produce INCOMPLETE_CONFIG cuando falta la configuración oficial.

CONCLUSIÓN
==========

DAT-01 está técnicamente implementada. El único criterio funcional que no puede cerrarse con datos reales es el conteo de inclusiones, cambios y exclusiones, debido a que no existe en el workspace documentación oficial que identifique la posición y los códigos de movimiento. El sistema está preparado para recibir esa configuración sin modificar el motor de procesamiento.
